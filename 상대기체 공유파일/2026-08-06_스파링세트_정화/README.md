# 스파링 세트 정화 — 에피소드 리셋 버그 (2026-08-06)

## 문제
우리 BT는 v29에서 고친 버그를 **스파링 상대는 그대로 갖고 있었다.**
- `Task_SyncMirror`: `if (runTime < lastRun)` = **한 번도 발동한 적 없는 리셋.**
  RunningTime은 생성자에서만 0이고 매 틱 증가하며, BTActionProvider.reset()이
  BT를 재생성하지 않으므로 되감기지 않는다.
- `Task_OneCircle` / `Task_SyncCircle`: **리셋 로직 자체가 없었다**(lastThr가 static).

→ 판이 바뀌어도 직전 판의 스로틀(및 sync는 선회 이력)을 물려받았다.

## 수정
셋 다 위치 점프(1틱 2km+) 방식으로 통일 — 우리 v29와 동일.
DLL 4종 재빌드: onecircle / sync / synccircle / shrink.

## 효과 (v32 고정, 15시드)
| 상대 | 정화 전 | 정화 후 | |
|---|---|---|---|
| **onecircle** | 3승 9무 2패 (14판) | **1승 12무 2패** | **달라짐** |
| sync | 1승14무0패 0.0231 | 1승14무0패 0.0231 | 완전 동일 |
| synccircle | 0승15무0패 0.0000 | 0승15무0패 0.0000 | 완전 동일 |
| shrink | 0승15무0패 0.0000 | 0승15무0패 0.0000 | 완전 동일 |

**해석:** sync/synccircle/shrink는 어차피 0대0으로 수렴하는 구조라
초반 스로틀 0.17초 차이가 결과를 못 바꾼다. **onecircle만 실제로 달라졌다.**
→ **v32의 "onecircle 3승"은 상대 오염으로 부풀려진 값이었다.**
   깨끗한 상대로는 1승. v32가 v29보다 나은 건 다른 상대에서 확고하지만
   onecircle 개선폭은 과대 보고였다.

## 내 실수 (기록)
정화 전 DLL을 `git show HEAD:...`로 꺼내려 했는데 **`*.dll`이 .gitignore에 걸려 있어
빈 파일(0바이트)이 나왔다.** 그걸 확인하지 않고 배치를 돌려 'old' 8판을 통째로 날렸다.
게다가 재빌드로 원본을 덮어써서 **정화 전 DLL은 복구 불가**(소스는 git에 있으니
되돌려 재빌드는 가능하지만 1시간).
→ **교훈: 스파링 DLL은 gitignore 대상이라 아카이브에 넣어야 보존된다.**
   그래서 이 폴더에 DLL+XML을 넣는다. 앞으로 스파링 세트를 바꾸면 여기에 스냅샷할 것.
