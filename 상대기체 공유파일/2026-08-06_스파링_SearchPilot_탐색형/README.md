# SearchPilot — 탐색형 상대기체 (채택)

사용자가 제시한 **"VP를 여러 개 찍어 최적을 찾는 기체"**의 구현.
RL이 **학습**으로 도달하는 정책을 **탐색**으로 근사한다. 대회에서 만날 RL 상대의 대리.
결정론적이라 재현·디버깅이 된다. `rehearsal_10hz.py`에서 상대 인자 `SEARCH`.

## 왜 이게 되는가 (2026-07-24 MPC 기각과 무엇이 다른가)
그때 기각한 건 **우리 제출 기체**에 대한 것이었다:
VP→Controller_CY(블랙박스)→6DOF를 예측할 모델이 없었고, 10Hz/100ms 예산이었다.
**상대기체엔 둘 다 해당하지 않는다:**
- VP를 쓸 필요가 없다. ACE처럼 **스틱을 직접** 낸다 → 가장 어려운 부분이 빠진다
- 로컬 스파링용이라 연산 예산 제약이 없다
- **포워드 모델은 이미 실측해 갖고 있다** (`corner_speed.py` 속도별 선회율, `turn_perf2.py` 뱅크별)

## ★ 이 기체의 진짜 값어치
스파링 상대로서만이 아니라 **"예측형 상대를 어떻게 깨뜨리는가"의 실험대**다.
위 실패들은 전부 **예측 기반 조종의 고유한 실패 방식**이고, 대회의 RL 상대에게도 적용된다:
- 후보/학습 분포 **밖의 상황**으로 몰면 무너진다
- 모델이 **낙관적인 영역**(고받음각·실속·급기동)으로 몰면 예측이 빗나간다
→ 우리 BT가 이 기체를 그런 상황으로 몰 수 있는지가 다음 실험이다.

## 한계 (정직하게)
- 근사 운동학이라 실제 6DOF와 어긋난다. 실속·고받음각은 못 맞춘다
- 상대 반응을 "현재 선회 유지"로 가정(open-loop). 근접 교전에서 부정확
- 구간별 탐욕이라 전역 최적이 아니다
- **여전히 15판 중 1판 자멸**한다
