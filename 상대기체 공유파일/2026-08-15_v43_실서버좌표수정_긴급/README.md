### 그런데 그냥 지우면 안 됩니다

운영측 말대로 삭제하면 **로컬 배치가 전부 깨집니다.** 로컬 경로(`ChangeData`)는 LLA를
만들어 넘기기 때문입니다(실측 `(37.9, 128.2, 7000.1)`). 그래서 **자동 판별**로 양쪽을 다 살렸습니다.

### "NED"인데 Z가 양수인 이유

문의 중 "서버의 Location은 이미 NED Cartesian"이라는 표현이 있으나, 실제 3번째 성분은
**고도(위가 양수)** 입니다.

- 실서버 spawn `z=4572.0` = 15,000 ft (양수)
- 실서버 로그 `MyZ=8450.36` (양수)
- 우리 `DECO_AltitudeCheck`가 `MyLocation_Cartesian.Z`를 `MinAlt`와 직접 비교 = 양수 전제

**깨진 v42에서도 Z만은 정상이었습니다.** `dD = LLA.Z − 0 = 고도`라서 그렇습니다.
`MyZ`는 멀쩡한데 `Dist`만 1억이었던 것이 이 설명과 정확히 맞습니다 — X/Y만 파괴됐습니다.

## 원인 — 좌표 규약이 두 경로에서 다르다

템플릿 헤더가 계약을 명시하고 있습니다.

```cpp
Vector3 Location;  // LLA Alt : Meter, 비헤비어트리로 입력할때는 LLA로 입력하지만
                   //                  내부에서 사용할때는 Cartesian으로 사용
```

즉 `Step()`에 넣는 값은 **(위도°, 경도°, 고도m)** 여야 하고, DLL이 내부에서 직교로 바꿉니다.

```cpp
Vector3 origin(OriLAT, OriLOn, 0.0);              // 37.914557, 128.181881
Vector3 MyLocationNEU = LLAtoCartesian(MyInfo.Location, origin);
//   dlat = LLA.X - BaseLLA.X;                    // 608.5 - 37.91 = 570.6 "도"
//   dN   = (M + alt) * dlat * PI/180;            // ≈ 6.3e7 m
```

그런데 **경로가 두 개**입니다.

| 경로 | 넣는 값 | 결과 |
|---|---|---|
| 로컬 (`ChangeData` → `Step`) | LLA (37.9, 128.2, 7000) | ✅ 정상 |
| **서버** (`policies.py` → `BuildPlaneData` → `Step`) | **직교 미터** (608.5, 6.1, 4572) | 🔴 위도 608.5도로 해석 |

**로컬 배치는 항상 `ChangeData`를 거쳐 LLA가 들어갑니다. 그래서 아무리 돌려도 안 터집니다.**
서버 경로를 타야만 터집니다. 로컬에서만 비교했으면 아무도 몰랐을 겁니다.

### 단위는 미터입니다 (피트 아님)

세 가지가 독립적으로 확인해 줍니다.

- 고도 `4572.0` ÷ 0.3048 = **정확히 15,000 ft**
- 이격 `608.5` — 대회 규정 초기 거리가 **610~914 m**. 피트면 185m로 규정과 안 맞음
- 속도 `200` — m/s면 정상, ft/s면 61 m/s로 F-16이 못 남

설계값이 피트로 떨어지는 숫자(15000ft, 2000ft)인데 **전달은 미터**입니다.
사격 사거리 152.4~914.4 m = 정확히 500~3000 ft인 것과 같은 패턴입니다.

## 고친 방법 — 입력 좌표계를 자동 판별

`CPPBehaviorTree.cpp` / `.h` 두 파일만 고쳤습니다. **트리(XML)는 v42와 한 글자도 다르지 않습니다.**

```cpp
// LLA면 위경도가 맵 원점 ±1도 안에 있다. 직교 미터면 크게 벗어난다.
// 한 대라도 직교로 보이면 그 프레임 전체를 직교로 본다(좌표계는 하나뿐이다).
if (CoordFrameMode != 2 &&
    DecideCoordFrame(MyInfo.Location, NumofOtherPlane, OthersInfo) == 2)
    CoordFrameMode = 2;

Vector3 MyLocationNEU = (CoordFrameMode == 2)
    ? MyInfo.Location                              // 직교는 그대로 쓴다
    : LLAtoCartesian(MyInfo.Location, origin);     // LLA는 종전대로 변환
```

**래치 방향이 중요합니다.** LLA는 고정하지 않고 **직교가 확인될 때만** 전환한 뒤 고정합니다.
LLA 입력은 항상 원점 ±1도 안에 머물러 오판할 여지가 없지만, 직교는 기체가 우연히
원점 근처 `(37.9, 128.2)m` 를 지나면 LLA로 오판할 수 있기 때문입니다.
이 방향이면 **로컬 경로는 이 분기에 절대 걸리지 않습니다.**

`LLAtoCartesian`이 `(dN, dE, dD)` = (북, 동, 상)을 돌려주고 Unreal도 X=북/Y=동/Z=상이라
직교 입력은 변환 없이 그대로 쓰면 됩니다. LLA로 되돌리는 왕복은 0.5% 오차가 납니다.

## 검증

### 1. 서버 경로가 실제로 고쳐졌나 — 실서버 실측 좌표를 그대로 투입

### 2. 축이 뒤집히지 않았나 — 거울상 검증

거리만 맞고 축이 바뀌면 기체가 거울상으로 납니다. 적기를 네 방향에 두고
LLA 경로와 직교 경로가 **같은 판단**을 하는지 확인했습니다.

| 적 위치 | LLA 경로 VP(N,E) / 롤 | 직교 경로 VP(N,E) / 롤 | |
|---|---|---|---|
| 북 +600 | (600.2, 0.3) +0.000 | (600.0, 0.0) +0.000 | OK |
| 동 +600 | (600.2, 604.1) **+1.000** | (600.0, 600.0) **+1.000** | OK |
| 남 −600 | (−0.3, 0.3) +0.000 | (0.0, 0.0) +0.000 | OK |
| 서 −600 | (600.2, −603.5) **−1.000** | (600.0, −600.0) **−1.000** | OK |

롤 방향이 네 방향 모두 일치. 직교 경로가 오히려 더 정확합니다(측지 근사 오차 없음).

### 3. 로컬 동작이 안 바뀌었나 — 15시드 × 3상대 시드일치

`_v43_verify.sh` 로 v42(`AIP_v40.dll`+`Rule_v42.xml`)와 v43(환경변수 없이 자기 XML)을
같은 90판으로 대조합니다. **한 판이라도 다르면 기각**이라는 기준을 미리 정했습니다.
