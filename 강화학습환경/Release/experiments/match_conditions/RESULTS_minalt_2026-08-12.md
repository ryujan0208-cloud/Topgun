## 왜 — 부분적으로만 설명된다 (과장하지 않는다)

### 발단: 실효 하한은 명목값이 아니다

`DECO_AltitudeCheck`는 **예측식**이다(v22c 도입):
```cpp
predAlt = CurrentAlt + (MySpeed_MS * sin(pitch)) * 5.0;
if (CurrentAlt < MinAlt || predAlt < MinAlt) -> ClimbOut
```
→ **실효 하한 = MinAlt + 5초치 하강량.** 급선회는 곧 하강이라 공격적으로 돌 때마다 걸린다.
기준선 실측: 30판 중 **27판**에서 발동, 발동 시 고도 **중앙 1657m**(최고 3063m).
명목 1000m보다 600~2000m 위다. ClimbOut이 BT 틱의 **10.4%**를 점유했다.

이는 v40이 고친 문제의 **남은 반쪽**이다. 조준 하한은 상대 고도 연동으로 **800m**까지
내려가는데 ClimbOut 실효 하한은 **약 1600m**였다.
(`CLAUDE.md`: *"조준하한과 MinAlt는 반드시 같이 낮춘다. 하나만 낮추면 벽에 부딪혀 에너지만 잃는다."*)

우리 조준 시간이 **6.6배**가 되고 P2·P3에서 **받은 피해가 0**이 된다.

### ★ 설명되지 않는 부분 — 그대로 적는다

고도대별 우리 ATA 중앙값과 사격 성립률:

| 고도대 | 기준선 ATA / 성립률 | M700 ATA / 성립률 |
|---|---|---|
| 1200~1700m | 128.2° / 0.18% | **69.8° / 5.37%** |
| 1700~2400m | 122.4° / 0.50% | **62.7° / 5.12%** |
| 2400~4000m | 119.3° / 0.59% | **74.7° / 5.00%** |
| **4000m 이상** | 101.7° / 0.61% | **51.6° / 2.28%** |

**개선이 모든 고도대에서 균일하다. 4000m 이상에서도 ATA가 101.7° → 51.6°다.**
그 고도에서는 `predAlt`가 1000m 아래로 내려갈 수 없어 **ClimbOut이 발동할 수 없다.**

→ 즉 **"ClimbOut 발동이 줄어서 좋아졌다"만으로는 설명이 안 된다.**
   개연성 있는 해석은 **연쇄 효과**다(초반 저고도에서의 한 번의 차이가 판 전체 궤적을 바꾼다).
   결합 동역학계에서 자연스럽지만 **직접 확인하지 않았다.**
   따라서 *"MinAlt 하나가 고고도 조준까지 개선한다"*는 인과 주장은 **하지 않는다.**
   ClimbOut 점유도 10.4% → 8.2%로 **조금만** 줄었다(효과 크기와 비례하지 않는다).

### ⚠ 집계 사고 — 중복 7판을 셀 뻔했다

legacy 1차 실행의 마지막 구간(junghwan)에서 로그가 4시간 동안 안 늘어나
**"행(hang)"으로 판단하고 프로세스를 강제 종료**했다. 그 뒤 그 구간만 재실행했다.

그런데 죽이는 순간 **파이프에 갇혀 있던 7판치 출력이 로그로 쏟아졌다.**
`grep`이 파일로 출력할 때 **블록 버퍼링**을 하기 때문이다.
두 로그를 합쳐 집계하니 junghwan이 **22판**(15 + 중복 7)이 되어
총계가 `117/37/3 +79.27`로 **부풀려졌다.** 판수를 세는 검증(`len(r)!=15`)이 잡았다.

**두 가지가 내 잘못이다:**
1. **로그 최종수정 시각은 신뢰할 수 있는 생존 신호가 아니다**(블록 버퍼링).
   그걸 근거로 멀쩡했을 수도 있는 실행을 죽였다. 정말 멈춰 있었는지 **확정할 수 없다.**
2. 집계 도구가 **판수를 검증하지 않았다면** 부풀려진 값을 그대로 보고했을 것이다.

→ 규칙: **배치 생존 확인은 로그 mtime이 아니라 `stdbuf -oL` / 트랙 파일 / 프로세스 CPU로 한다.**
   **집계는 항상 기대 판수와 대조한다.**
