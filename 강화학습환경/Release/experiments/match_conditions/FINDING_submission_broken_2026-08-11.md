# ★★★ 제출본이 v40이 아니었다 — 8/9~8/11 이틀간 · 2026-08-11

## 무엇이 잘못됐나

제출 패키지 = `AIP_final.dll` + `Rule_forTraining.xml`.

```
Rule_v40.xml          MinAlt="1000"   <- v40 채택본. 아카이브도 이 값
Rule_forTraining.xml  MinAlt="1800"   <- v32 값. 내용이 2026-08-05 이후 안 바뀜
```

v40 채택 커밋 `80d7d6a`(8/9)는 **`Rule_v40.xml`만 새로 만들었고** 제출용 XML은 건드리지 않았다.
DLL은 8/9에 v40 코드로 다시 빌드됐다. 그래서 제출 조합이 **"v40 DLL + v32 MinAlt"**가 됐다.

## 왜 치명적인가 — v40은 두 변경이 **쌍**이다

```cpp
AIM_FLOOR = clamp(상대고도 - 300, 800, 1500)   // Task_LeadPredict  (DLL 안)
DECO_AltitudeCheck MinAlt: 1800 -> 1000         // Rule XML          (XML 안)
```

`CLAUDE.md`에 이미 적혀 있던 경고다:
> ⚠ **조준하한과 MinAlt는 반드시 같이 낮춘다. 하나만 낮추면 벽에 부딪혀 에너지만 잃는다**
> (`divefree` 기각 사유). 무조건 낮추는 것도 안 된다(`lowfloor`는 kwon −3으로 기각).

제출 조합은 정확히 그 반쪽이다. 조준점은 800m까지 내려가는데 트리는 1800m에서
`ClimbOut`으로 넘어가 **추격이 중단**된다.

## 확인 — 정적 분석과 동작 검증 둘 다

### 정적: 두 DLL은 같은 소스 빌드다
`AIP_final.dll`(=`AIP_final_v40.dll`, SHA256 동일)과 `AIP_v40.dll`은 465,920B로 크기가 같고
**86바이트만 다르다.** 차이 13구간의 정체:
- PE 타임스탬프 5곳 (빌드 시각)
- XML 경로 문자열 74B (`./Rule_forTraining.xml` vs `./Rule_v40.xml`)
- 그 문자열 길이 차이로 밀린 상대주소 6곳(1B씩) + 체크섬 1곳

**코드는 동일하다. 다른 것은 XML뿐이다.**

### 실측: 고도 분포가 벽에 걸린다
대회조건 OBFM_RED 30판에서 우리 고도 실측:
- **1800m 아래로 내려간 판: 27 / 30**
- 1800m 미만 체류 **10.9%** / 1000m 미만 체류 **0.0%**

즉 v40 하한(1000m)은 한 번도 안 걸리는데, 제출본 하한(1800m)은 **거의 매 판** 걸린다.

### ★ 동작 검증 — 같은 15시드, 같은 상대(jh2), legacy 조건

| 상대 | 제출본 `AIP_final`+`Rule_forTraining`(1800) | 채택본 `AIP_v40`+`Rule_v40`(1000) | 시드 일치 |
|---|---|---|---|
| **jh2** | **3 / 0 / 12** — 순이득 **−8.517** | **12 / 1 / 2** — **+9.433** | **0 / 15** |
| ACE | 14 / 0 / 1 — +0.885 | 15 / 0 / 0 — +1.557 | **0 / 15** |

**두 상대 모두 시드 일치가 0이다.** jh2전은 15시드 중 11개가 승패까지 갈렸고,
제출본의 12패는 대부분 격추다(ownHP 음수).

★ **ACE에서는 차이가 작다**(14승 vs 15승). 이건 모순이 아니라 일관된다 —
1800m 벽은 **싸움이 낮게 내려갈 때** 걸리고, 그건 상대가 강할수록 자주 일어난다.
→ **약한 상대만 보면 이 결함은 안 보인다.** 검증 상대 선택이 결과를 가린다.

대조점 두 개가 결론을 굳힌다:
- 채택본 **12승 1무 2패**는 `CLAUDE.md`의 v40 기록("jh2전 4승11패 → 12승2패")과 **일치**한다.
  → **v40 자체는 멀쩡하다.**
- 제출본 **3승 12패**는 v32의 jh2 성적(4승 11패)과 사실상 같다.
  → **제출본은 v40의 개선이 통째로 무효화된 상태 = 사실상 v32다.**

## 교정

`Rule_forTraining.xml`의 `MinAlt="1800"` → `"1000"`. 교정 후 `Rule_v40.xml`과 **실질 내용 동일**.
망가진 원본은 `Rule_forTraining_BROKEN_v32minalt.xml.bak`로 보존한다(증거).

## 왜 못 봤나 — 재발 방지

`CLAUDE.md`에 이미 **"제출본이 낡을 수 있다"**는 항목이 있었다. 다만 그때 사례가
*"`AIP_final.dll`이 v27인 채로 있었다(XML은 v27~v32 동일해서 안 보였음)"* 라
**"DLL을 의심하라"**로 좁게 읽혔다. 이번엔 **정반대로 XML이 낡았다.**

→ 규칙을 고친다: **버전 채택 시 DLL과 XML을 *쌍으로* 대조한다.**
   해시/크기만으로는 안 된다. **채택본과 제출본을 같은 시드로 돌려 성적이 일치하는지 본다.**
   (v40 채택 때 `_v40_verify.sh`로 "게이트판 vs 기본판" 일치는 확인했는데,
    **제출 빌드는 그 검증에 포함하지 않았다.** 그 구멍이 이번 사고다.)

⚠ 규정집 제6조 4항: *"참가자의 코드 결함, 학습 모델 오류, 환경 적응 실패는
  재경기 사유에 해당하지 않는다."* 제출 전 검증 실패는 전적으로 우리 책임이다.

## ★ 교정 검증 — 완전일치 확인 (`_submit_fixed.log`)

교정 후 `AIP_final.dll` + `Rule_forTraining.xml`(1000)을 **환경변수 없이** 돌려
`AIP_v40.dll` + `Rule_v40.xml`과 대조했다.

| 상대 | | 제출본 | 채택본 | **시드일치** |
|---|---|---|---|---|
| jh2 | 교정 전 | 3/0/12 −8.517 | 12/1/2 +9.433 | **0 / 15** |
| jh2 | **교정 후** | **12/1/2 +9.433** | 12/1/2 +9.433 | **15 / 15** |
| ACE | 교정 전 | 14/0/1 +0.885 | 15/0/0 +1.557 | **0 / 15** |
| ACE | **교정 후** | **15/0/0 +1.557** | 15/0/0 +1.557 | **15 / 15** |

순이득이 소수 3자리까지 같다. **제출본 = 채택본 v40임이 동작으로 증명됐다.**
"성적이 비슷하다"가 아니라 **시드별 완전일치**를 기준으로 삼은 이유가 여기 있다 —
교정 전 ACE는 14승 vs 15승으로 "비슷"해 보였지만 시드일치는 0이었다.

## 남은 일

1. 교정본으로 재검증 — `AIP_final.dll` + 교정 `Rule_forTraining.xml`이
   `AIP_v40.dll` + `Rule_v40.xml`과 **시드별로 일치**해야 한다.
2. A(Evade 제거)가 legacy를 통과하면 같은 파일에 Evade 분기 제거를 얹어 v41 패키지로 간다.
