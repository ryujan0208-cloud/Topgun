# ★★★ dt 버그 — 10Hz 제출 조건에서 상대 선회율을 7~9배로 잘못 읽고 있다

**v15부터 v32까지 안 풀린 "과근접해서 못 쏜다"의 정체다.**

## 코드 경로

```cpp
// CPPBlackBoard.cpp:6
DeltaSecond = 0.0166666;                          // 1/60. 생성자 값.

// LibMain.cpp:317 — DLL이 노출하지만 호스트가 **부르지 않는다**
void SetBehaviorTreeDeltaTime(int OwnShipID, double DT)

// Task_LeadPredict.cpp
const int HIST = 12;                              // 12 "BT 틱"
omegaNow = fwdOld.angleBetween(TgtFwd) / (HIST * dt);
```

- `native_bt.py`가 선언한 DLL 함수는 6개뿐: `ChangeData` `CreateBehaviorTree` `GetVP`
  `RemoveBT` `Reset` `Step`. **`SetBehaviorTreeDeltaTime`은 없다.**
- 이력 버퍼 `fwdHist`는 **BT 틱마다** 채워진다.
- 제출 조건은 `ACTION_REPEAT=6`. 대회가 제공한 `unreal/policies.py`가
  `pair_count % action_repeat == 0`일 때만 BT를 부르고 나머지는 캐시를 쓴다.
  **우리 `rehearsal_10hz.py`의 `RepeatProvider`와 같은 구조 — 에뮬 문제가 아니라 실전 조건이다.**

→ 12틱 = **1.2초** 실제 경과인데 `HIST * dt` = 12 × (1/60) = **0.2초**로 나눈다.

## 실측 (코드만 읽고 결론 내지 않았다)

같은 상대를 두 속도로 돌려 `[ACTIVE]` 진단의 `om=`과 트랙 CSV의 실제 선회율을 대조했다.
(`tools_diag/omega_check.py`, 로그 `_omega_probe.log`)

| 실행 | BT가 쓰는 om | 실제(1.2초 창) | 비율 |
|---|---|---|---|
| repeat=1 (60Hz) onecircle | 0.149 rad/s (8.5°/s) | 8.75°/s | **0.98** |
| **repeat=6 (10Hz) onecircle** | **1.466 rad/s (84.0°/s)** | 9.36°/s | **8.98** |
| repeat=1 (60Hz) jink | 3.4°/s | 4.4°/s | 0.78 |
| **repeat=6 (10Hz) jink** | **0.678 rad/s (38.8°/s)** | 5.4°/s | **7.25** |

**60Hz에서는 맞고 10Hz에서만 틀린다. 오차가 repeat 배수를 따라 커진다** — dt 가설이
예측한 형태 그대로다. 예측 배수는 6, 실측 7~9(om 표본이 6초마다 1개라 표본 편차).
그리고 **84°/s는 F-16이 낼 수 없다**(우리 실측 최대: 하강나선 순간 42.8°/s, 수평선회 지속 11.3°/s).

## 결과: TailSlot이 사격 불가 구역에 찍힌다

```
R    = tgtSpd / omega                clamp [200, 8000]
phi  = 300.0 / R                     clamp [0.05, 0.6]
슬롯거리 ≈ 2R·sin(phi/2)             의도: 300m
```

| 상대 (10Hz 실전) | BT가 믿는 omega | R | **슬롯거리** | 실제 omega | 실제 R | 올바른 슬롯 |
|---|---|---|---|---|---|---|
| **onecircle** (307 m/s) | 84.0°/s | 209m | **124m** | 9.4°/s | 1880m | 300m |
| jink (306 m/s) | 38.8°/s | 451m | 267m | 5.4°/s | 3270m | 300m |

**사격 최소거리는 152.4m다. onecircle 상대로 124m를 조준한다 — 쏠 수 없는 거리다.**

상대가 세게 돌수록 omega 오차가 커지고 `phi`가 상한 0.6에 걸려 **조준점이 더 가까워진다.**
방향이 정확히 반대다.

### 이것이 설명하는 것 (전부 기존 실측과 일치)
| 관측 | 설명 |

| onecircle 1승 12무 2패 (최약 매치업) | 가장 세게 도는 상대 = 오차 최대 = 슬롯 124m |
| "뒤 잡은 시간 91%, ATA 중앙 7도, 사격 0틱" | 위치·조준은 정상. **거리만 미달** |

| `RunningTime`이 작동하지 않는다 (v29에서 우회) | 같은 원인. 6배 느리게 흐른다 |

## 영향 범위

- `Task_LeadPredict`: `omegaNow`(v21 게이트), v17 궤도 블록의 `omega`/`R`/`phi`
- `Task_LeadPredict`: `LHIST = 6`("0.1초 창" 주석) — v27 `losRate`도 같은 배수로 틀림
- `RunningTime` 전반 (이미 우회됨)

## 주의 — 고치는 것이 곧 개선은 아니다

**v32의 모든 상수는 이 부풀려진 omega 위에서 경험적으로 조정됐다.**
절제 실험에서 v17은 중요도 1위(빼면 −18승)였다. 즉 **틀린 채로 잘 작동하고 있다.**
dt를 고치면 v21/v17 게이트 발동률이 급감하고 R·phi가 전부 바뀐다 — 사실상 새 기체다.

→ **반드시 사전등록 후 9상대 15시드로 판정한다.** 최소 두 가지를 나눠 시험할 것:
- **근본 수정**: 실제 경과시간을 BT가 스스로 추정(`|Δ위치| / 속도`)해 dt를 교정
- **국소 수정**: 게이트는 그대로 두고 궤도 블록의 R 계산만 교정
